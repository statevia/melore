# spec-pick-next

完了直後・着手前などに、**次に着手する計画項目 / Spec**を根拠つきで提案し、ユーザーと合意する。

## 前提

- ワークスペースが Melore リポジトリであること。
- 次のいずれかの文脈があること（無い場合は計画文書から現状把握してよい）。
  - 直近完了した Spec / コミット
  - ユーザーが気にしている領域（検索精度 / 鮮度 / MCP ツール / explain など）
- Markdown / Spec 更新が必要なら `.cursor/skills/markdown-spec-authoring/SKILL.md` に従う。

## 実行してほしいこと

1. **現状把握**（並列可）:
   - [`docs/guides/implementation-plan.md`](../../docs/guides/implementation-plan.md) の Phase と完了の定義
   - [`docs/guides/agent-task-accuracy-plan.md`](../../docs/guides/agent-task-accuracy-plan.md) の改善計画
   - [`docs/guides/search-gaps.md`](../../docs/guides/search-gaps.md) の未対応の検索漏れ
   - [`docs/guides/mcp-tool-candidates.md`](../../docs/guides/mcp-tool-candidates.md) の追加候補
   - [`docs/evaluation.md`](../../docs/evaluation.md) の受け入れ基準の未達
   - `.spec/specs/` にある Spec の `tasks.md`（未完了・Cancelled の有無。無ければ省く）
   - ユーザーが言及した依存・ブロッカー（他 PR、未 push など）

2. **候補を 1〜3 件に絞る**:
   - **推奨 1 件**を先頭にし、根拠を短く書く（依存が揃っている／同一トラックの自然な続き／ブロッカー解消後など）。
   - 代替候補は「いつ選ぶか」を 1 行で添える。
   - 前提未充足・設計矛盾がある候補は、着手前に直す点を明示する（推測で実装方針を確定しない）。
   - 完了済みで計画文書が古い項目は、次タスク候補ではなく **文書更新 / archive** として分けて書く。

3. **ユーザーへ確認**（独断で実装に入らない）:
   - 推奨項目と、着手する最初のタスク（あれば）
   - 代替を選ぶ場合の条件
   - 併せてやるべきハウスキーピング（`/spec-archive`、計画文書の更新）があれば列挙
   - **判断はユーザーに委ねる**旨を明記する

4. **合意後のみ**（ユーザーが「これで」と指示したとき）:
   - 選んだ Spec の `tasks.md` や、該当する計画文書の状態を現状に合わせる（必要なら）
   - 変更した Markdown は `npx markdownlint-cli2 "<パス>"` で確認する
   - 実装着手は別途の明示依頼があるまで行わない（本コマンドの主成果は **合意と計画の整合**）

5. **報告**:
   - 推奨 / 代替の一覧
   - ユーザー確認待ちの論点
   - 合意済みなら更新したパス一覧

## 選定の目安（優先の考え方）

| 優先しやすい | 後回ししやすい |
| --- | --- |
| 直前の改修の続き、前提が完了したもの | 候補止まりで受け入れ基準が無いもの |
| 同一トラックで依存が揃っているもの | インデックス再構築を伴う大きなスキーマ変更 |
| `search-gaps.md` や `eval` で効果を測れるもの | 効果を測る手段が無いもの |

## ユーザー向け短文（チャットへの貼り付け用）

直近の完了状況と `docs/guides/` の計画文書を見て、次に着手する項目を 1〜3 候補で提案し、合意後に計画文書を更新してください。実装には入らないでください。
